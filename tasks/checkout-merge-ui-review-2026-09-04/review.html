What changed, and why

Duplicate checkouts were stranded as separate list records

Was

The Checkouts list had no way to select two same-event open checkouts for repair, so a duplicate battery checkout remained split from the original custody record.

Now

Staff/admin users can select compatible open checkouts and choose Merge matching checkouts; separate kiosk handoff timestamps no longer block the repair, the checkbox and three-dot action sit in a shared top-right rail in card view, the oldest checkout survives, and the other records become cancelled history.

A visible merge could lose physical custody history

Was

Reparenting only the visible item lines would risk leaving scan sessions, stock movements, numbered-unit allocations, photos, reports, and return activity attached to the cancelled source.

Now

One serializable transaction moves custody-linked rows, numbered battery units, bulk quantities, and live-activity references, then writes before/after audit receipts for the target and each source.

Same event is necessary but not sufficient

Was

A broad same-title or same-person merge could combine different event windows, locations, people, or started/returned custody.

Now

Preview and mutation require exact event set, title, requester metadata, custody scope, and location; the modal resolves return-time and reservation-link differences explicitly, while partial, completed, excluded, duplicate, or already-returned custody remains blocked.

Return/source mismatches stopped the repair before review

Was

The merge endpoint rejected checkouts as soon as their return windows or source reservation IDs differed, so an operator could not decide which context should survive.

Now

A dedicated modal lists the available return times, accepts an adjusted due-back, and lets staff choose the surviving reservation link. The selected time is checked against combined availability and recorded in due-date and merge audit history.
