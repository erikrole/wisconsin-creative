Detail headers — one shared primitive

The four detail headers in the app were four hand-maintained copies of one idea. Two of them had no heading element at all. One carried a decorative wash the design language forbids. They now share a DetailPageHeader primitive, the 32px controls behind them are gone, and a contract test holds it.

What changed, and why

All four conversions are presentational. No data fetching, permission gate, role branch, upload path, or tab behavior was touched.

Four hand-maintained copies of one shell became one component

Was

ItemHeader, BulkSkuHeader, and BookingHeader had each independently converged on the identical string rounded-lg border border-border/50 bg-card px-4 py-4 shadow-xs sm:px-5, while /users/[id] used a different rounded-xl card with a decorative radial-gradient(… rgba(160,0,0,0.045) …) overlay. docs/DESIGN_LANGUAGE.md lists decorative gradients under what to avoid.

Now

src/components/DetailPageHeader.tsx owns the shell with media / status / title / subtitle / meta / actions / footer slots, plus a sideBySideAt breakpoint because the routes genuinely differ: bulk has two compact buttons, item and booking have wide two-row action columns.

Two of the four headers had no heading element

Was

On /items/[id] the asset tag and on booking detail the booking title both rendered as styled <span>s inside plain divs. Neither page had an h1, so the document outline and screen-reader heading navigation had nothing to anchor to.

Now

Both render inside the primitive's h1. Measured cost: item detail grows 167px → 181px and its tag drops 32px → the shared 30px scale; booking detail grows 254px → 264px with no title size change, since its span was already 30px at this width.

Title styling was reimplemented per route, mostly as dead code

Was

Three different expressions: text-[28px] sm:text-[32px] plus inline font-family and weight; text-2xl font-black sm:text-3xl; and on the collaborator branch of the same user page, text-2xl font-bold tracking-tight.

Now

Bare h1 inheriting the one rule in globals.css. Verified in the browser: on an h1, that base rule already beat the Tailwind size and weight utilities, so on /users/[id] and /bulk-inventory/[id] those classes were never taking effect. The rendered title there is unchanged; only /items/[id], where the title was a span, actually shifts.

Eleven header controls sat below the 40px target baseline

Was

size="sm" resolves to h-8 (32px). It was on the user Admin actions trigger, the Retry and Back to users recovery buttons, both award-dialog mode toggles, the item Open checkout and Reserve buttons, and the booking Actions, Edit, and Extend buttons.

Now

All explicit h-10 with the shared active:scale-[0.96] press treatment.

The primitive grew a footer slot rather than forcing booking detail to drop its summary

Was

Booking detail's four summary facts — schedule, pickup location, gear count, linked event — live inside the header below a rule. No other detail header has them.

Now

DetailPageHeader takes a footer slot that owns the border-t and spacing, and the route supplies its own grid. The alternative was leaving booking detail on its own copy of the shell, which is what created this problem in the first place.

The user detail skeleton did not match the header it stood in for

Was

A bare 48px avatar and two lines with no card, so the shell jumped when data arrived.

Now

Same card shell and a 64px avatar, matching the loaded footprint.

The detail tabs were still full of 32px targets

Was

Behind the headers, the user and item tab bodies carried 29 more size="sm" and h-8 controls: save, retry, copy URL, generate token, rotate token, month navigation, load more, clear filters, award, revoke, detach, and both combobox triggers.

Now

All at h-10. Ten of them were multi-line JSX tags that a line-based grep misses entirely — the contract test found them because it matches across newlines, and one arrow function's > truncated a naive tag regex into producing a duplicate className, which TypeScript caught.

The records that got this wrong are corrected, not just worked around

Was

tasks/design-language-route-conformance-checklist.md rated detail pages "mostly conforming" with a "low follow-up" of visual smoke coverage. docs/DESIGN_LANGUAGE.md named PageHeader as the only header primitive, so a detail route with identity media had no documented option but to invent one.

Now

The checklist carries a dated correction and a Detail Page Headers section. The design language names DetailPageHeader, says when to pick it over PageHeader, and records that restating the heading scale on an h1 is dead code. tests/detail-page-header-source.test.ts enforces all of it.

The 40px baseline was an app-wide program, and it is now closed

Was

The conformance checklist implied targets were handled, marking route after route "Strong" with "40px commands." No one had counted.

Now

A brace-aware scan put it at 169 controls across 66 files. All 146 text-label controls are now at h-10, and tests/operational-target-baseline.test.ts enforces it across src/app and src/components rather than an allowlist. Two exceptions are explicit and reasoned in the test itself: icon-only controls (the density conflict) and FormCombobox, which stays at h-9 so it aligns with the h-9 Input and SelectTrigger beside it.

The 40px rule and the density rule contradict each other

Was

docs/DESIGN_LANGUAGE.md requires 40px icon-only targets and also requires repeated rows to stay dense. Twenty-three controls sit where both apply — four 24px approve/deny/edit/delete icons inside one compact availability chip, for instance.

Now

Recorded as an open conflict naming all twelve affected surfaces, with the two candidate fixes and what each costs. Resizing triples the chip height; routing through OperationalRowActions makes approve/deny two clicks on a primary decision. Left for a per-surface product decision rather than settled by regex.

Verification

  • TypeScript: clean. Lint: clean across src/app, src/components, and tests.
  • Full suite: 3615 passing, 0 failing, 536 files.
  • Build: npm run build:app compiles. Docs: codemaps current.
  • Three contract tests, 17 assertions, each with a self-check proving it fails on a real regression.
  • Captures: Playwright Chromium, device scale 2, 1280px and 900px, light and dark. Baselines from git show HEAD or a path-scoped git stash.
  • Caught by captures, not tests: the bulk tablet regression. Caught by review, not the codemod: the FormCombobox misalignment.

What this does not prove

  • The sweep found a regression I introduced. The codemod raised FormCombobox to 40px, which misaligns it against the h-9 Input and SelectTrigger it sits beside in dialog forms. Reverted, and the form-field baseline is queued as its own decision rather than settled by a button sweep.
  • The captures come from a component harness, not the authenticated routes. A temporary unauthenticated page rendered pre- and post-change markup with fixture content so each pair could be matched exactly. Authenticated proof on the real routes with real data is still open, consistent with the standing local-auth limitation in docs/GAPS_AND_RISKS.md.
  • The harness route and capture script were deleted; they are not in the diff.
  • Counting is the trap here. A line-based grep undercounts these badly: multi-line JSX tags are invisible to it, an arrow function's > truncates a naive tag regex, and a size="sm" carrying an h-10 override is already compliant. My first three counts were all wrong in different directions — 13, then 275, then 170 — before a brace-aware parser settled it at 169. Two routes I had flagged, /operations and /signatures, turned out already clean.
  • Rendered as static stand-ins, so unexercised: the avatar upload dropdown and crop dialog, the badge award dialog, the item image modal and Actions menu, the bulk image modal, and the booking Actions menu, inline title editing, and sync indicator. Source is unchanged but no interaction was driven.
  • Still below 40px, deliberately left: the booking reference copy button and the refresh affordance are 11px and 10px inline text controls, not buttons in the operational sense. They predate this change and deserve their own decision rather than a silent resize.
  • Corrected in the repo's own records: tasks/design-language-route-conformance-checklist.md rated detail pages "mostly conforming, low follow-up." That did not hold: these were the four largest detail surfaces, none used a shared header, and two had no h1. The row is now corrected with a dated note. (An earlier draft of this page also faulted the checklist's /items typography entry — that entry is about the list page's table headers, a different surface, and it was accurate.)
  • Not touched: the 13 sub-40px controls inside the user and item tab components, which are a separate sweep from the headers.
