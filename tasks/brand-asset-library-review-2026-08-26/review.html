Brand assets — implementation review

Resources now has a separate, Google Drive-style Brand assets library for logos, fonts, reference files, templates, and the viewable brand-guide PDF. The library keeps one stable file row while each replacement becomes an immutable version.

Storage boundary

Blob + Prisma

Vercel Blob stores private binaries; Prisma/Neon stores folders, file identity, versions, and upload intents

Replacement model

File → History

The current pointer advances to the next version; earlier files remain available

Seeded content

No seed data

The current Preview PDF was uploaded explicitly during testing; migrations create no content

What changed, and why

The source implementation is supplemented by a clean authenticated desktop check and a side-by-side comparison with the supplied Google Drive reference. The review is intentionally presented as reference comparison plus runtime evidence rather than a matched before/after pair: the V1 component was untracked in the starting worktree, so a trustworthy same-product baseline capture is unavailable.

Resources was guide-only

Was

The existing Resources page handled Markdown guides and supporting references, but had no durable file-library boundary for brand binaries.

Now

A URL-backed Brand assets tab isolates folders, file metadata, current versions, History, PDF viewing, and downloads without changing guide filters or Markdown semantics.

Replacing a file would lose continuity

Was

A simple upload/delete workflow would force people to manage duplicate names and would remove the prior file from the product record.

Now

A stable logical file is unique within its folder. Uploading a new version advances an explicit current pointer and preserves the previous version in authenticated History.

Large binaries need a storage boundary

Was

Routing a roughly 21.7 MB guide through a small server form upload would add unnecessary transport and timeout pressure, while a public URL would weaken access control.

Now

The client uses @vercel/blob/client with a short-lived actor-bound intent; the dedicated private store is read through an authenticated app proxy with no raw Blob URL returned.

The first file-library layout was too dense

Was

The Brand assets surface repeated the same context across a large intro card, separate controls, recent cards, folder cards, and file cards with many always-visible actions.

Now

The surface now follows a Drive-style hierarchy: folder rail, working New/Home/Recent/Starred navigation, breadcrumb, one compact toolbar, suggested-folder tiles, and a unified table with secondary actions behind the row menu.
