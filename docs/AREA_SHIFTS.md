# AREA: Shift Calendar & Scheduling

## Document Control
- Area: Shift Calendar & Scheduling
- Owner: Wisconsin Athletics Creative Product
- Last Updated: 2026-09-03
- Status: Active — implemented V1 with ongoing hardening

## Purpose

Replace Asana-based shift scheduling with a native shift calendar in Wisconsin Creative. Auto-generate shifts from ICS-synced calendar events using sport-specific templates, support staff assignment plus approval-first student requests for open Student slots, and provide a trade board for Admin-approved student shift swaps.

## Key Concepts

- **ShiftArea**: VIDEO, PHOTO, GRAPHICS, SOCIAL, COMMS, LIVE_PRODUCTION
- **ShiftWorkerType**: Internal planned staffing kind; UI and notifications must display Staff or Student, never raw enum abbreviations
- **SportConfig**: Per-sport Staff and Student shift counts for home/away events per area
- **Settings-owned Student call time**: Home and Non-game offsets are the shared fallback for Student coverage. Away/road and Neutral Student assignments retain stored windows for conflict/readiness and staff operations but expose event timing without a call-time value in worker-facing projections. Staff and collaborator coverage retains the event window internally but exposes no call-time value or event-time substitute; all-day events retain date-only boundaries.
- **ShiftGroup**: 1:1 with its source CalendarEvent. A combined operational event retains both source events but uses only the canonical event's ShiftGroup as the shared crew; the secondary group is archived and excluded from release.
- **Pending schedule**: One private, versioned staff editing copy per ShiftGroup. Future edits restart a durable ten-minute quiet period and reconcile automatically; the same editor publishes an ended event synchronously as a silent backfill while worker-facing reads retain the last released schedule until that write completes. Each command keeps a bounded actor-owned before/after history, so named Undo and Redo can restore one staged change at a time through the server's version boundary; batch Revert remains the explicit all-change escape hatch.
- **Assignment provenance**: `ShiftAssignment.source` distinguishes manual staffing, preview-approved auto-fill, and reservation-managed schedule work. Reservation lifecycle cleanup can release only the last category.
- **Trade Board**: Area-filtered board where students post shifts they can't work; other students in the same area can claim them. A claim is a request: an Admin approves or declines it, and the poster keeps the shift until then.
- **Contextual open-slot claims**: The expanded Schedule disclosure and Event detail Crew table own the student `Claim shift` action and its `Awaiting approval`/`Withdraw` state through one shared helper. The legacy `ShiftDetailPanel` remains read-only for student claim submission; Staff/Admin still use the shared versioned working-copy editor for crew changes.
- **StudentAvailabilityBlock**: Weekly or ad hoc student availability signal used by scheduling. Weekly blocks describe recurring class windows; ad hoc blocks can cover an inclusive date range and all-day time away. Existing blocks read as approved cannot-work advisory conflicts; newer blocks can express prefer, dislike, pending time off, approved time off, or denied time off.

## Information Architecture

### Schedule Page (`/schedule`)
1. **Page Header** — title and a "More" overflow menu for New event, Combine events (with suggestion count), Trade Board (with open-trade count), and Export CSV; students keep a direct Trade Board button. Combine events is Staff/Admin-only and preview-first. A dismissible inline prompt opens a matching pair's server preview immediately; the dialog retains manual selectors and dismissible suggested pairs.
2. **Schedule attention bar** (`ScheduleReadiness` + shared `OperationalStatusRail`) — compact strip with next call plus up to three priority-ordered clickable exceptions for the nonzero staffing, gear-gap, data-quality, conflict, request, trade, source, and personal-shift queues. Additional exceptions remain accounted for in Details, and a calm all-clear state appears only when health data is complete.
3. **Details panel** — one collapsed-by-default expander (shared `OperationalMetricCard` grid) holding the full readiness metrics and, for staff/admin, the review-first Automation review cards: staffing, auto-fill preview, publish readiness, blockers, sources, and cleanup
4. **Work queues** — URL-backed `queue` state for Needs staffing, Conflicts, Pending requests, Trade approval, Gear gaps, My calls today, and Stale source
5. **Data quality queue** — staff/admin Schedule health flags visible events with missing sport context, missing opponents, missing venue/location mapping, future archived status, or shifts without sport metadata. The queue filters the list to affected events and routes cleanup back through existing Event detail, Locations, and Venue Mappings ownership.
6. **Filter Bar** (`ScheduleFilters`) — quiet `OperationalToolbar` with View, Venue, My Shifts, a Filters popover (Past, Archived, Sport, Area, Coverage), source-signal status, and the active queue banner
7. **View Toggle** — List | Week | Calendar (persisted to localStorage)
8. **List View** (`ListView`) — the event triage, crew-setup, and compact crew-management workstation. Staff use each event row's overflow menu to choose Home, Away, or empty crew setup, open the shared focused Manage crew sheet, or open Event detail. The row disclosure remains the primary multi-event workstation and mounts the same versioned editor used by the focused sheet and Event detail; workers retain read-only schedule context, with eligible Student open slots exposing the shared Claim/Awaiting approval helper inline. Event detail adds the deeper event, gear, and recent-change context around that editor.
9. **Week View** (`WeekView`) — shared period navigation (prev/next/Today), 7-day orientation with event counts, readable time/venue/title cards, coverage and open-slot truth, My Shifts highlight, and expanded active days on mobile. Every staff event card opens the shared focused crew sheet: configured events enter `WorkingCrewEditor`, while unconfigured events offer deliberate Home, Away, or empty setup and immediately hand the returned group into that editor. Workers continue to open Event detail.
10. **Calendar View** (`CalendarView`) — shared period navigation, a desktop month grid with readable 40px event chips and day counts, and a complete mobile month agenda with the same event, coverage, and open-slot semantics. Desktop chips and mobile cards use the same staff crew-sheet handoff and setup choices as Week; workers continue to open Event detail.
11. **ShiftDetailPanel** — legacy read-only schedule context plus archive and preview-first auto-fill for remaining non-staff contextual reads. Staff crew assignment management now lives in the shared focused crew sheet, expanded Schedule row, and Event detail; Student open-slot claims remain in the expanded Schedule row and Event detail.
12. **Open Work / Trade Board** — sheet overlay with area/status filters and separate `Trade Posts` and `Open Shifts` browse sections, plus my trade posts, blocked context, and resolved trade history. A trade post names another student's coverage request; an open shift is an unassigned published Student slot.
13. **Assignment review** (`/schedule/assign`) — month-level coverage, conflict, and open-slot review plus preview-first bulk assignment. Per-cell live mutations are retired; individual crew changes open the Event's private working schedule editor.
14. **Auto assign** (`AutoAssignDialog`) — one staff/admin entry point on the Schedule page, and the same dialog behind `/schedule/assign`. Scope is sports (multi-select, empty means all), period (this week, this month, this semester, full season, or the caller's own range), scheduling class (everyone, students only, staff only), and an optional area. Selecting sports shows each roster with a link to change it. **Assignment is purely roster-based**: for an event with a sport, only people assigned to that sport are candidates, in both the bulk engine and the per-event auto-fill; events with no sport have no roster to check. Area fit and scheduling class still decide which slot a candidate can take. The preview is built on demand and rolls proposals up per worker — who is being added and to how many shifts — before anything is staged. It also counts what a run would leave undone: events that would release short a position, and events skipped for unreleased staff changes. **Full crews only** holds back any event that cannot be filled completely, so a run never half-crews an event. Applying stages a working copy per event on the existing auto-release timer; nothing publishes directly, and the staged batch stays cancellable from the same dialog until the timer fires. Approved time off blocks every scheduling class, not students only.
15. **Sport auto-assign policy** (`SportConfig.autoAssignPolicy`) — each sport decides how far automation may go: `FULL_CREW` fills staff and student slots, `STAFF_ONLY` fills staff and deliberately leaves student slots open for students to request through Open Work, and `HOLD` proposes nothing. A sport with no configured policy defaults to `FULL_CREW`, so behavior is unchanged until a policy is set. Migration `0138` seeds the Big 6: Football `HOLD`; Men's and Women's Basketball, Men's and Women's Hockey, and Volleyball `STAFF_ONLY`. Both the bulk engine and per-event auto-fill honor the policy, and the apply transaction re-reads it before writing. Student slots left open by `STAFF_ONLY` are out of scope rather than an unfilled crew, so they never count against the full-crew check. Events on a held sport are excluded from the scope query entirely rather than loaded and discarded, so they neither consume the `MAX_BULK_EVENTS` cap nor pull a shift-group tree per event; their number is reported from a separate count. Every auto-assign route is rate limited, reads included, and every roster mutation — travel changes included — writes an audit entry.
16. **Sport setup wizard** (`SportSetupWizard`) — a sport-by-sport pass over the two things auto assignment needs, policy and roster, Big 6 first. Reached from Settings → Sports and from the Change control on any roster inside Auto assign. Each change saves as it is made, and the roster half reuses the existing `/api/sport-configs/[sportCode]/roster` endpoints. Travel rosters are edited in the same step: a star on each roster chip toggles `StudentSportAssignment.defaultTraveler` through the same PATCH the Event travel card uses, and the step names who currently travels. **Away games are crewed from the travel roster**: for an event with `isHome: false` on a sport that has anybody marked `defaultTraveler`, only those people are candidates. A sport that has marked nobody falls back to its full roster, so away games never silently empty for a sport whose travel roster has not been set; `no_travel_roster` names the case where the travel roster exists but nobody on it fits. Home games and events with no recorded venue side are unaffected. Travel state also orders the Event travel card. **Match another sport** copies a chosen sport's policy onto the current one, optionally adding its people and their travel flags — additive only, so a roster built by hand is never deleted by a match. **Skip** moves to the next sport without changing anything. Settings → Sports reads policy, roster size, and travel counts from the same `/api/schedule/sport-setup` endpoint the wizard writes through, and each sport card links back into the wizard at that code, so the two surfaces cannot drift.

### Event Detail Page (`/events/[id]`)
1. Event identity card — status plus Synced, Manual, or Edited source state, event timing, opponent, venue, and source context
2. Link summary — crew fill, gear links/gaps, travel state, and source edit state
3. Shift Coverage card — merged with Command Center (staff/admin: versioned working-copy crew editor plus gear summary; students: read-only 5-col table with the shared claim helper for eligible open Student slots)
4. Crew gear state — staff/admin can distinguish assignment-linked gear, event reservations, pickup-ready gear, checked-out gear, and missing gear from the Crew table
5. Action CTAs — "Reserve gear for this event" and staff/admin "Review schedule"; normal web checkout creation is not exposed because kiosk owns custody

### Dashboard Integration
1. **My Shifts card** — upcoming assigned shifts with area, time, "Prep gear" button
2. **Upcoming Events card** — events with assigned user avatars
3. **Stat strip** (staff/admin only) — Overdue, Due today, Active checkouts, Reserved (clickable, links to filtered views)

### Cross-Area: Scan Feedback
- Haptic vibration feedback on scan success/error (shipped in `useScanSubmission` hook, documented in `AREA_CHECKOUTS.md`). Audio feedback not yet implemented — schedule-adjacent for shift-linked scan flows.
