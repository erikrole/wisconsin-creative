## Direction
Badges are lightweight recognition for every active user inside the existing ops app. Staff and admins earn badges on the same profile surface as students. Automatic badges come only from durable facts Wisconsin Creative already captures. Hidden easter eggs may come from a signed-in app foreground event only when the server evaluates the condition from trusted time.

## Core Rules
1. `BADGES_ENABLED !== "true"` returns before any badge evaluator work, database query, or side effect.
2. Operational badge events attach to service-level outcomes: kiosk checkout/pickup open, checkout return completion, trade completion, and a confirmed assigned shift ending. `onShiftsWorked` is evaluated nightly from `morning-refresh`; the cron is when the completed assignment is noticed, not the earning event. A narrow easter-egg exception accepts authenticated app foreground events, but the server's institution timezone decides whether a hidden rule matches.
3. Legacy app checkout scan stubs remain non-events. They stay kiosk-gated 403 routes and award nothing.
4. Badge definitions are seeded by immutable `key`. Typos are fixed by retiring a definition with `active=false` and creating a new key.
5. User awards are idempotent by `(userId, definitionId)`.
6. Request-scoped badge events claim a durable `BadgeEventReceipt` keyed by user, event type, and canonical source before changing any counter. Checkout and return use the booking ID, trade uses the trade ID, and app open uses the local date plus the rule-specific condition (hour, weekday, holiday, or other server-evaluated calendar fact) in the configured institution timezone.
7. Migration and profile reconciliation repair objectively completed automatic thresholds. A returned badge profile never shows completed progress without an award row. A repaired award is dated from the evidence that earned it -- the Nth qualifying event for a counted goal, or the latest contributing evidence for a distinct-count or streak goal -- never from the moment of the request. Dating a repair `now()` both lied on the shelf and, because `/api/badges/recent` selects by `awardedAt`, fired a celebration for months-old work triggered by whoever opened the profile.
8. Deactivated users keep historical badges.
9. Admins are treated as staff for recognition. They can earn badges and compare profiles like everyone else.
10. Rarity's numerator and denominator count one population. Holder counts filter on `user.active` because `eligible` does; counting historical awards against the current roster let a share exceed 1.0.
11. A revoke resolves a `StudentBadge` row. The profile serves `awardId` for exactly this, and no client may substitute the definition id.
12. Every web badge surface draws its glyph from `src/components/badges/badge-artwork.ts` and its disc from `badgeRarityMedallionClass` in `src/lib/badges/display.ts`. A badge cannot change picture between the celebration that announced it and the shelf it lands on.
13. Checkout-open credit is immutable across ownership transfer. A pre-open transfer moves future credit; a post-open transfer preserves checkout count, category breadth, gear-family, and single-checkout challenge credit for the original opener while the new custodian owns the return outcome.

## Data Model
- `BadgeDefinition`: seeded catalog. Uses immutable `key`, display copy, icon name, category, kind, trigger, threshold, rule key, active flag, and sort order. The canonical launch catalog is seeded by migration `0064_seed_badge_definitions`, and `prisma/seed.mjs` mirrors the current post-`0100_badge_catalog_rebalance` catalog so reseeding cannot regress automatic definitions.
- Custom manual badges are also `BadgeDefinition` rows. Admin-created custom badges use a generated `custom_` key, `trigger="manual"`, `kind=RULE`, `category=MILESTONE`, and no evaluator wiring.
- `StudentBadge`: legacy-named earned badge row for any user. Unique on `(userId, definitionId)`, supports `AUTO` and `MANUAL`, optional `awardedById`, and optional staff note.
- `BadgeStreak`: per-user streak state. `ON_TIME_RETURN` remains active. Historical `SCAN_SUCCESS_COUNT` and `SCAN_CLEAN` rows are retained but are no longer mutated or returned to clients.
- `BadgeEventReceipt`: durable request-event and immutable credit ledger. Unique on `(userId, eventType, sourceKey)` and claimed inside the same Serializable evaluator transaction as streak and award writes. Checkout-open receipts use the opened checkout ID, so later `Booking.requesterUserId` changes cannot move credit.
- `Booking.completedAt`: durable checkout completion timestamp. On-time badge counts use this field with a legacy `updatedAt` fallback for pre-field rows, so later booking edits do not change return eligibility.
- Automatic fun rules share one derivation module for evaluator writes and profile progress. Return rules read completed custody rows (`startsAt`, `endsAt`, `completedAt` with an `updatedAt` fallback, and whether any check-in report exists) and are evaluated above the on-time early return, because a long custody and a same-day turnaround are true whether or not the gear came back on time. Trade rules read completed trade rows rather than a count, and credit short-notice cover to the claimer. Checkout rules use credited booking contents, canonical top-level category families, actual bulk `checkedOutQuantity`, serialized item rows, `Booking.kitId`, and `Booking.startsAt`. Weeks are Monday-anchored in institution time so a Sunday-evening checkout is not filed under the following week, and an all-battery run requires a non-empty family set containing only batteries. The rebalanced v8 rules avoid new raw-volume ladders: checkout derivations add week bursts, month spans, category/family/kit/event breadth, mixed/full-context loadouts, and actual item volume; return derivations add clean timing, no-intervention returns, and clean streaks; trades add two-sided participation; shifts add sport-area pairs, month span, home/away and schedule spectrum, away wins, recorded-result coverage, winning records, win streaks, bounce-backs, battle-tested history, and site depth. Shift rules use confirmed ended assignments, `CalendarEvent.isHome`, `CalendarEvent.sportCode`, `CalendarEvent.result`, `CalendarEvent.site`, `CalendarEvent.locationId`, `CalendarEvent.opponent`, `Shift.area`, the effective call window (`ShiftAssignment.callStartsAt`/`callEndsAt`, then `Shift.callStartsAt`/`callEndsAt`, then `Shift.startsAt`/`endsAt`) in the institution timezone, and `ShiftAssignment.hasConflict`. Missing schedule facts do not count, and copy says assigned rather than attended. Checkout context rules use credited `Booking.eventId`/`BookingEvent`, `sourceReservationId`, and `shiftAssignmentId`; return-problem rules use check-in report type, due-date changes, and the same 15-minute late boundary. Sport codes and opponents are compared case-insensitively, doubleheader days are grouped by institution-local date rather than UTC, and a shift that crossed local midnight counts as having run past 10 p.m.
- `SystemConfig["badges.peerVisible"]`: default `true`; controls peer visibility for another user's badge tab.
- Badge evaluator transactions run with Serializable isolation and retry once on Prisma write conflicts so duplicate source-key retries re-read streak state before mutating.

## UI Direction
- Primary user experience is a `Badges` tab on `/users/{id}` for students, staff, and admins. `/profile` already redirects to user detail.
- A dedicated `Badges` item lives under the internal `Operations` sidebar group for the catalog and group-award workflow.
- No badge count, chip row, or recognition chrome in the profile hero.
- The badge tab uses shadcn primitives as a medallion-first trophy shelf: one summary band, then five shelf sections with no drill-in level. A shelf previews its first 10 tiles and offers `Show N more`; the flat always-visible shelf was designed against a 30-badge catalog and the catalog is 115 definitions now, 98 of them visible once the v8 expansion deploys -- 23 rows and roughly 4,400px of scroll, nearly all of it identical locked discs for anyone new. Collapsing never applies on top of a filter, because a filter is already the reader narrowing on purpose. Within a shelf the order is earned (newest first), then locked goals already in motion (nearest completion first), then catalog order, so the previewed rows are the ones worth previewing. The summary band leads with the earned count rather than a completion percentage: the catalog is built to be mostly unearned, so a percentage headline tells a strong student "11%" and calls it their score. Completion still rides the bar, and includes only visible automatic goals, so manual recognition, hidden surprises, and retired history cannot lower it.
- Shelves group badges into Gear Flow, Reliability, Legacy Scan Awards, Teamwork, and Staff Picks. Goal shelves show earned/total; legacy and staff recognition shelves show earned count only.
- Badge tiles lead with the medallion (locked keeps its own icon dimmed rather than a padlock -- true on web since 2026-08-27, on iOS since 2026-07-22 -- rarity = disc fill) over the name and one quiet meta line; status/rarity/manual chips live only in the detail dialog. Recent awards keep the one-week glow and a New chip. The meta line is the earned date, else real progress `x/y`, else the definition's own description. It used to fall back to `{threshold} required` or `Unlocks automatically`, neither of which says what earns the badge -- and the sentence that does was already in the payload. The name and meta slots reserve two lines each and cards fill their grid cell, so a row keeps one baseline whatever the copy length.
- Both clients draw the same medallion: one disc for every badge, told apart by rarity. Earned is a rarity gradient under a white glyph; locked is a quiet muted wash behind the badge's own dimmed icon. The per-category coin/hex/shield/stack silhouettes were removed from iOS on 2026-07-22 -- `stack` rendered as a notched square behind an offset second square, which read as a clipping fault rather than a medal -- and from web on 2026-08-27, where they had never cut a real silhouette at all: the rim, the rarity ring, and the shadow all belonged to a rounded rect and the shape survived only as a faint outline drawn inside it, so at the 48-56px the shelf renders, all four looked the same. Category identity is carried by the shelf a badge sits on, not by its outline. The web disc palette lives in `--badge-{rarity}` / `--badge-{rarity}-deep` in `globals.css`: fixed across both themes like the native accents, and picked for contrast against the white glyph rather than against the page -- `--orange` carries white at 2.2:1, under the 3:1 WCAG non-text minimum, which is why the discs do not reuse the semantic palette. On iOS the badge card is a horizontal earned shelf, newest first, plus live streak rows and a closest-to-earned progress row; the gallery sheet keeps the same five collection sections.
- A few surprise badges stay hidden from the locked grid until earned. The count is reported once per page, under the shelves, alongside the summary band's `Hidden` stat -- it used to render as a tile on every shelf that happened to hold a hidden definition, which put four copies of the same sentence on one screen.
- The badge profile API loads active definitions plus historical earned inactive definitions in one Prisma call that includes the user's award row.
- The web tab leads with a closest-to-earned row, matching the native badge card. Ties break on how few steps remain, so `9/10` leads `90/100`.
- The detail dialog shows the served holder count under the rarity chip, which is what makes the rarity word believable.
- `GET /api/badges` excludes hidden-until-earned definitions. It is the one badge surface with no client-side filter behind it.
- The badge profile API adds progress only when it can derive it from real counters or streak state. Manual and unsupported rule badges remain rule-based with no fake progress bar.
- With `BADGES_ENABLED` off, badge APIs return disabled/empty payloads before any badge table query. This keeps un-migrated local or preview databases from failing on badge UI routes.
- `/reports/badges` is staff analytics only and follows existing report layout patterns. It shows aggregate award metrics, manual award rate, user leaderboard, badge distribution, underused active definitions, recent manual recognition, and recent awards.
- The `Badges` Operations page is the primary admin award surface; the existing user admin actions menu remains a convenient shortcut.
- Admins can also use `Users > More > Award badge to matching users` to award one manual badge to every active user matching the current directory filters. The server resolves the filter group again, caps one request at 200 active users, skips existing `(userId, definitionId)` awards, and returns awarded/skipped/failed results for review. Inactive users are never included; custom definitions are created once and then reused across the batch.
- Manual award selection remains available for the two general recognition badges and admin-created custom badges. The ten new fun badges are automatic and never appear as staff-awarded definitions.
- Award notifications are persistent inbox entries that link to `/users/{userId}?tab=badges`. Automatic awards notify too, titled `Badge earned` against the manual path's `Badge awarded`, because nobody handed those over. Both respect `notificationPrefs.badges` and both write the notification inside the same transaction as the award, so a badge and its telling cannot diverge.
- Only a real earning event notifies. Profile self-repair deliberately does not: reconciling eight historical awards must not arrive as eight inbox entries. `createManyAndReturn` is what keeps this honest -- it returns only the rows an event actually inserted, so a replayed event awards nothing and therefore says nothing.
- Manual awards are admin-only through the existing user admin actions menu. They can target any active user, persist `source=MANUAL`, `awardedById`, and an optional note, and create a persistent inbox notification unless `User.notificationPrefs.badges === false`.
- Web and the signed-in iOS app show a queued, rarity-tinted reward popup for awards earned after that device establishes its cursor. The initial read establishes a server cursor and intentionally returns no history, so sign-in or migration cannot replay the full catalog as celebrations.
- Kiosk checkout, pickup, and return completion responses include newly earned awards for the selected user. Individual scan responses no longer award badges. The native kiosk collects completion awards across the flow and extends the success screen into the reward moment without interrupting custody work or requiring a user session on the shared device.
- Reward presentation is additive and failure-isolated. A failed reward read must never change a committed checkout, pickup, or return result. Reduced Motion removes decorative movement while preserving the award content and accessibility announcement.

## Native Badge Artwork
`ios/Wisconsin/Shared/BadgeEarnedCelebration.swift` owns the one Lucide-to-SF-Symbol map (`BadgeArtwork`) and the one rarity palette (`BadgeRarity`) for every native badge surface. The file is a member of both the `Wisconsin` and `WisconsinKiosk` targets, so nothing needs its own copy. The map is one-to-one and must answer every seeded catalog icon plus every custom-badge picker option; `tests/ios-badge-icon-coverage.test.ts` fails on an unmapped name, a collision, or a second table appearing in a view. Rarity colour is Common brand red, Uncommon blue, Rare orange, Legendary purple -- the celebration's original values. Web matches this vocabulary through its own `--badge-{rarity}` tokens, deepened where a white glyph needed the contrast.

## Rarity
Rarity is computed from how many people hold a badge, not from a hardcoded list. `getBadgeRarity` in `src/lib/badges/display.ts` buckets holder share among active users: >=50% Common, >=20% Uncommon, >=5% Rare, below that Legendary. Two guards keep scarcity honest -- a badge with zero holders, or a definition younger than 30 days, has not had a chance to be earned, so it falls back to the difficulty-based rating. The API serves `rarity`, `holders`, and `rarityProvisional` on every badge row; web and iOS render the served value rather than keeping their own tables. `rarityProvisional` is true whenever the rating came from the difficulty fallback rather than measured scarcity. It matters at catalog-expansion time: the v8 migration adds 50 definitions at once, so a large share of the catalog sits inside the proving period at launch and would otherwise present a heuristic guess in the same voice as a real holder count. The web detail dialog labels the chip `{Rarity} (provisional)` and replaces the holders line with `Too new to rate by scarcity yet`.

## Streaks
The badge profile payload exposes `ON_TIME_RETURN` as `streaks[]`, and native Home renders it on the badge card. Historical scan counter and streak rows remain stored but stay out of profile payloads.

## Rollout
1. Slice 1 ships schema, seed, service skeleton, feature flag, and docs with the flag off.
2. Later slices wire one domain event family at a time and add focused tests.
3. Preview verification flips `BADGES_ENABLED=true`, exercises kiosk/trade/manual flows, then flips it back off to prove rollback.
4. Production enablement happens only after preview verification.
5. Migration `0110_badge_rewards` must deploy before the updated evaluators are enabled. It creates receipts, freezes historical checkout-open ownership from audit history, repairs completed automatic awards, retires scan goals, and seeds the new catalog. Optional reward response fields preserve client compatibility during rollout.
