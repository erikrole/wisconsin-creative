# Events Area Scope

## Document Control
- Area: Events
- Owner: Wisconsin Athletics Creative Product
- Last Updated: 2026-09-03
- Status: Active

## Direction
Make athletics schedule data the operational backbone for booking and checkout workflows.

## Scope Clarifier
1. Event sync supports booking creation context and linkage.
2. V1 does not require a standalone Upcoming Events section on dashboard mobile or desktop.
3. Missing or stale event records must never block non-event booking operations.

## Now (Implemented)
1. Ingest UW Badgers ICS feed — idempotent upsert by `external_id` (ICS UID). Source URL: `webcal://uwbadgers.com/api/v2/Calendar/subscribe?type=ics&locationIndicator=H`.
2. Normalize records into CalendarEvent model for operational use.
3. Support sport filtering for checkout selection (30-day event picker window via `resolveEventDefaults`).
4. Persist booking linkage fields (`eventId`, `sportCode`).
5. Events and Schedule reads use an app-timezone day boundary and `endsAt > startOfTodayInAppTz(...)` for current-work windows, so in-progress and all-day events remain visible through the local day.
6. Calendar source deletion: `DELETE /api/calendar-sources/[id]` — nullifies `eventId` on linked bookings (SET NULL before cascade), then deletes source and its events.
7. Calendar sync hardening: per-event error isolation so one malformed ICS event cannot crash the entire source sync.
8. Batch DB operations in sync pipeline for performance (avoid N+1 query patterns).
9. Production sync diagnostics: structured logging for missing event counts and sync failure details.

## Now (Implemented — cont.)
10. **Unified Schedule page** — merged `/events` + old `/schedule` into single `/schedule` page. List view with date-grouped events + coverage badges. Calendar view with month grid + coverage indicator dots. Unified filters (sport, area, coverage, past events). Trade Board as tab. ShiftDetailPanel integration. Old `/events` page removed (detail page `/events/[id]` unchanged). Sidebar shows single "Schedule" entry.
11. **Venue Mappings moved to Settings** — `/settings/venue-mappings` page with add/delete/list. Removed from events page.
12. Calendar Sources management remains at `/settings/calendar-sources` (unchanged).
13. Manual Calendar Source sync uses a short database-backed per-source lease, so concurrent sync clicks return 409 instead of running duplicate external fetch and shift-generation work.
14. Daily calendar sync runs through `morning-refresh` at 08:00 UTC, before the 09:00 UTC notifications cron. Manual sync remains the on-demand path for urgent schedule changes.
15. Repeated hard daily sync failures are tracked per source. Starting at 3 consecutive hard failures, active admins receive in-app `calendar_sync_failure` notifications, and Admin Fix Today includes the repeated-failure count for the source.

## Now (Implemented — cont.)
16. **Manual event edits (sync-safe)** — Staff/admin can edit event title (inline pencil → dialog), display label, event type, opponent, and pickup location on the event detail page. Event type supports Home, Away, Neutral, and quiet Non-game classification for one-off events such as media days. Manual title and event type survive ICS re-sync via lock flags (`summaryLocked`, `isHomeLocked`) on `CalendarEvent`; event-type locking also preserves the manually selected opponent or cleared non-game opponent. Revert-to-synced re-derives from `rawSummary` + `rawLocationText`. Edits are audited.
17. **Soft archive** — `morning-refresh` cron stamps `archivedAt` on events older than 4 months. List API excludes archived events by default; `includeArchived=true` surfaces them. No data deleted — full event + booking + travel history preserved for future Wrapped-style stats.
18. **Manual multi-day all-day events** — Staff/admin can create one manual all-day event that spans multiple dates. The Schedule New Event sheet uses inclusive start/end date copy while preserving the stored exclusive end boundary. `/api/calendar-events` and `/api/shift-groups` use overlap windows so schedule list/month/week views and crew coverage stay visible on every covered date without duplicating the underlying event record.
19. **Schedule source freshness signal** — Staff/admin Schedule views show a compact source signal in the filter toolbar. It distinguishes manual visible events, imported visible events, healthy calendar sources, stale/never-synced sources, disabled sources, source errors, and source-status load failures without changing ICS sync semantics.
20. **Morning-refresh automation digest** — `morning-refresh` now includes a read-only Schedule automation digest in its response after daily maintenance. The digest reports sync additions/updates, generated shift counts, archive counts, stale trade cleanup, pending pickup cleanup, publish readiness, auto-fill preview candidates, unresolved blockers, and source state. It is observability only; manual Settings sync and staff review actions remain the mutation paths.
21. **Crew operations cleanup** — Schedule event-row menus own Home, Away, or empty crew setup and open the compact shared working-copy crew editor for day-to-day assignment, replacement, slot, call-window, and timed-release management. Event detail Crew calls the same editor with deeper event, gear, and history context; workers keep a read-only crew table. Template-review and attendance controls are not surfaced.
22. **Event identity normalization** — Calendar sync, manual event creation, and event edit/revert paths share opponent and venue text cleanup. Opponents drop ranking/source boilerplate such as `No. 9` or `University of`, while venue matching normalizes source spellings such as `Wis.` to `WI` without overwriting `rawLocationText` evidence or confusing calendar venue with pickup location.
23. **Manual event date/time correction and timing-mode conversion** — Staff/admin can edit the start and end of a manually authored event from Event detail and switch it between an inclusive all-day date span and a local timed window. The audited serializable mutation keeps the target date semantics intact, moves live crew windows, slot and personal call overrides, private working copies, published snapshots, acknowledgement/conflict state, and published-schedule notifications by the same offsets. Imported event timing remains calendar-source-owned, and existing gear reservation windows remain independent.
24. **Shared team Scoreboard** — The current server-owned Scoreboard season is aggregated from Schedule events with two bounded event reads. Team coverage counts unique completed confirmed events, work credits count each active visible person once per event, the official record counts each eligible resolved W/L/T game once, and record credits count each person once per resolved game. Ties count as half a win for the server-owned rate, while the raw `[T]` marker remains source evidence. Multiple shifts on one event never multiply a person’s credit; exhibitions, scrimmages, and alumni matches stay in work coverage but remain outside the official record. Exact Sport, cleaned Schedule venue, normalized opponent, and canonical Home/Away/Neutral site filters stack with AND semantics, and the same filtered event sets drive totals, all four breakdowns, Snapshots, and per-person summaries.

25. **Added workers** — An admin can add any person, internal or collaborator, to a past or future event from Event detail ("Add worker") without creating a shift or an assignment. Rows are one-per-person-per-event, optionally noted, and audited on the event. Scoreboard totals, per-person Scoreboards, profile game records, worked-event counts, and shift badges read added workers alongside active assignments and still count each person once per event. An added worker contributes the event's own sport, site, result, opponent, and venue to badge rules but claims no area or call window, and an all-day row stays out of the hour-of-day rules. Backfill badge recognition is fully silent: every newly earned badge is still recorded, but the backfill creates no badge notification, including when scheduled assignments also cross a threshold. Schedule, working copies, published crews, crew coverage, My Shifts, trades, acknowledgements, notifications, and ICS do not read them. Staff can see an event's worker list; only admins can add or remove one. A failed read renders as an explicit error with a retry rather than an empty roster, so a missing table or a broken deploy cannot hide behind "no one has been added". Note the vocabulary: "credit" stays the Scoreboard's word for what it counts, "worker" is the person on record. See D-057.

26. **Schedule list is one continuous timeline** — The list view is a single chronological run of events with the past above today and the future below, replacing the earlier past-events switch and Upcoming/Past/All scope; past is a direction you scroll, not a mode you select. The page title and filter bar stay pinned below the app-shell header while the timeline runs beneath them. Their measured top and combined bottom edges are published as `--schedule-sticky-top` and `--schedule-sticky-bottom`, so the Schedule frame never covers the global header and day headers plus the today anchor stack below both sticky frames. The app-shell header also owns the highest non-modal sticky layer (`z-40` above the Schedule frame's `z-30` and day headers' `z-10`), so a retiring day header cannot paint over the global bar while it leaves its section. It opens anchored on today, positioned in a layout effect before paint so the page appears already there rather than visibly scrolling, then holds that position through a ResizeObserver rather than for a fixed stretch of time — late-rendering avatars and readiness cards push today down, a single re-anchor landed ~60px off, and a timed settle pass expired before the readiness row arrived and left it ~38px off. Two arrivals are exceptions to the today anchor. A back navigation keeps the browser's own restored position, so opening an event from months back and returning does not lose the reader their place. A refresh keeps the position too, restored from a recorded offset rather than the browser's own restoration — the list renders asynchronously, so the browser's restore lands after the anchor has already snapped the page up to today. Reload classification also checks that Schedule was the app shell's initial route; the document-level navigation type stays `reload` after client navigation, so using it alone would incorrectly restore an old offset on a later fresh Schedule visit. That restore re-applies on every layout change until the target is reachable without clamping, because the list renders in stages and a single pass would drop it while the document was still short, leaving the reader at the top. A fresh visit still opens on today. The pinned bar carries its own top spacing and a shadow once stuck, detected with a sentinel because CSS cannot tell a sticky element that it is currently stuck. Scroll ownership is claimed from input events only (wheel, touch, key, mousedown), never the scroll event itself, which also fires for the anchor's own programmatic scroll; once the reader moves the page, no automatic scroll runs again. Today always renders as a row even with nothing scheduled, so a quiet day still anchors the view. A "Jump to today" control appears once today leaves the viewport in either direction. The window loads up front in 200-row pages rather than on scroll, because area, coverage, and my-shifts filter client-side over loaded rows and progressive loading would make a filtered list look empty until the reader scrolled far enough. The first page reports `total`, so the remaining pages are requested together rather than one round trip at a time; when a route reports no total the loader walks pages instead of guessing a count. Rows are deduplicated by id, since offset paging can return the same event twice if one is added between requests. Hitting the 15-page cap is reported in the list rather than silently truncating it. Every automatic scroll is gated on whether the reader has moved the page themselves, so a background refetch or a filter change never yanks them back to today, and loading archived events preserves the reading position while the rows prepend above — measured on the running app as a 1,400 → 19,905 scroll shift against 18,505px of prepended history. The old document height and position are retained before the archived query can render, including when history is enabled from the Filters popover, so an immediate cached response cannot race the preservation anchor. Requesting archived history counts as the reader taking the wheel, and the today anchor stands down while that restore settles so two automatic scrolls never compete. The top of the list names the archive floor and offers "Load archived events" instead of just stopping. A failed shift-group read leaves events listed without crew counts rather than emptying the schedule. Calendar and week views are unchanged and stay driven by their explicit month or week window.

27. **Schedule sticky navigation stack** — On the continuous list, the app-shell breadcrumb remains pinned below the 48px global header. The Schedule title/filter frame measures both layers and pins below them, so fresh today anchoring, reload restoration, and Event-detail Back restoration move only the timeline while Home / Schedule remains visible.

27. **Ended-event edits use the standard Schedule backfill path** — A schedule change to an event whose live end time has passed publishes through the normal crew editor immediately, clears any pending release state, and skips the ten-minute cooldown. The correction is fully silent across schedule, follower, gear-prep, badge, in-app, push, and email channels; the editor and release notice show no “assignees notified” copy. The published assignment is immediately visible to Scoreboard work totals and event history, including result-less events, while official W/L/T record math remains resolved-only. `EventWorker` remains the separate record for work that had no planned shift slot.

28. **Quarter-hour Event and Schedule authoring** — Timed manual event creation/correction and Student call-window editing use native 15-minute increments and normalize an explicitly saved off-grid value forward to the next quarter-hour. Event detail preserves untouched legacy off-grid values when only another field changes. All-day inclusive/exclusive date semantics, imported-calendar time ownership, audited crew-window propagation, private working-copy release behavior, and independent gear reservation windows are unchanged.

29. **Student claims are contextual and approval-aware** — Eligible open Student slots expose one shared `ClaimShiftAction` in expanded Schedule rows and the Event detail Crew table. The helper shows `Claim shift` or `Awaiting approval`/`Withdraw`, refreshes both read surfaces after the canonical pickup or withdrawal route, and never appears in the legacy `ShiftDetailPanel`. Event detail remains the deeper staffing surface: Staff/Admin use the shared working-copy crew editor, while students see the read-only crew table plus their own pending-request state. The shift-group read returns only the current viewer's `REQUESTED` request, and a submitted pickup creates durable in-app plus best-effort push review notifications for active visible Admin reviewers.

30. **Combined operational events** — Staff/Admin can combine two overlapping source events from the same sport family at the same normalized venue into one Schedule row and one shared crew. Schedule proactively surfaces a dismissible suggestion and count for future standalone pairs that share the Schedule day, sport family, normalized venue, overlapping window, and compatible meet/opponent; Review opens the server preview immediately. That preview states how many assigned crew stay and how many empty secondary draft slots retire. Both `CalendarEvent` records remain source-owned and syncable; the secondary points to the canonical primary. The primary is selected deterministically in favor of an existing published or assigned crew. A second published or assigned crew blocks the operation. An unpublished, unassigned secondary setup is archived, and its private draft is retained at a superseding version with release disabled so an already-queued workflow cannot publish it. The combined row spans the earliest start through latest end. Primary Event detail names both source events with individual times and offers Staff/Admin an audited Undo that restores the retained secondary draft without publishing or releasing it; direct navigation to the secondary resolves to the primary while combined. See D-060.
